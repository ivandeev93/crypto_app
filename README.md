# Crypto Price Tracker

Асинхронный backend-сервис для сбора, хранения и предоставления истории индексных цен BTC и ETH с криптовалютной биржи [Deribit](https://www.deribit.com/).

Сервис автоматически получает цены `btc_usd` и `eth_usd` каждую минуту, сохраняет результаты в PostgreSQL и предоставляет REST API для получения истории и последней цены.

## Возможности

- Получение индексных цен BTC и ETH через публичный API Deribit.
- Периодический сбор данных с помощью Celery Beat.
- Асинхронные HTTP-запросы через `aiohttp`.
- Хранение истории цен в PostgreSQL с использованием SQLAlchemy Async.
- REST API на FastAPI для получения сохранённых данных.
- Фильтрация истории по дате и получение последней цены.
- Повторные попытки выполнения фоновой задачи при ошибках.
- Контейнеризация приложения и зависимостей с Docker Compose.
- Модульные тесты для проверки логики приложения.

## Архитектура

Проект организован с разделением ответственности между слоями приложения.

- `api` — HTTP-эндпоинты FastAPI и схемы API.
- `domain` — бизнес-сущности, интерфейсы репозиториев и бизнес-логика.
- `infrastructure` — клиент Deribit, модели базы данных, сессии и реализации репозиториев.
- `services/tasks` — фоновые задачи Celery.
- `core` — конфигурация приложения и настройки Celery.

Поток обработки данных:

1. Celery Beat запускает задачу сбора цен каждую минуту.
2. Celery Worker вызывает клиент Deribit.
3. Клиент получает индексные цены BTC и ETH.
4. Полученные значения преобразуются в доменные сущности.
5. Репозиторий сохраняет данные в PostgreSQL.
6. FastAPI предоставляет доступ к сохранённым данным через REST API.

Каждая запись содержит тикер, значение цены и время получения в формате Unix timestamp.

## Запуск через Docker Compose

### 1. Клонирование репозитория

```bash
git clone https://github.com/ivandeev93/crypto_app.git
cd crypto_app
```

### 2. Настройка переменных окружения

Создайте файлы `.env` и `.env.docker`, ориентируясь на шаблон `.env.example`, если он присутствует в репозитории.

Пример необходимых переменных:

```dotenv
DATABASE_URL=postgresql+asyncpg://crypto_user:your_password@db:5432/crypto_db
POSTGRES_USER=crypto_user
POSTGRES_PASSWORD=your_password
POSTGRES_DB=crypto_db
REDIS_URL=redis://redis:6379/0
DERIBIT_BASE_URL=https://test.deribit.com/api/v2/public
```

Замените `your_password` на собственный пароль.

Для Docker Compose имя хоста PostgreSQL — `db`, а Redis — `redis`. Эти имена соответствуют сервисам в `docker-compose.yml`.

При локальном запуске приложения вне Docker адреса сервисов и значения переменных окружения необходимо настроить соответственно.

**Важно:** не публикуйте файлы с реальными паролями и другими секретами в GitHub.

### 3. Запуск приложения

```bash
docker compose up --build -d
```

Команда собирает образ приложения и запускает следующие сервисы:

| Сервис | Назначение |
|---|---|
| `api` | REST API на FastAPI |
| `celery` | Celery Worker и Beat |
| `db` | PostgreSQL |
| `redis` | Брокер сообщений Celery |

### 4. Проверка работы

Откройте документацию Swagger UI:

http://localhost:8001/docs

Альтернативная документация ReDoc:

http://localhost:8001/redoc

Просмотр логов приложения:

```bash
docker compose logs -f api
```

Просмотр логов фоновых задач:

```bash
docker compose logs -f celery
```

Остановка контейнеров:

```bash
docker compose down
```

Данные PostgreSQL хранятся в Docker volume `db_data`. Обычная команда `docker compose down` сохраняет этот volume.

## API

API предоставляет операции для получения истории цен, последнего значения и данных за определённый период. Для запросов используется обязательный параметр `ticker`.

Поддерживаемые тикеры:

- `btc_usd`
- `eth_usd`

Все методы чтения используют HTTP GET.

Точные URL эндпоинтов и названия параметров следует смотреть в Swagger UI: `/docs`.

Примеры логики запросов:

- Получить все сохранённые значения для выбранного тикера.
- Получить последнюю известную цену.
- Получить историю цен с фильтрацией по дате.

## Периодический сбор данных

Celery Beat запускает задачу сбора цен с интервалом 60 секунд.

Для каждого тикера клиент обращается к публичному методу Deribit `public/get_index_price`.

Если при получении цены одного тикера возникает ошибка, она записывается в лог, а обработка второго тикера продолжается. Ошибки сохранения в базе данных приводят к откату транзакции и передаются Celery для обработки политики повторных попыток.

В текущей конфигурации Celery Worker и Beat запускаются в одном контейнере. Это упрощает запуск проекта и подходит для небольшого приложения.

## Миграции базы данных

Проект использует Alembic для управления схемой PostgreSQL.

Перед запуском миграций убедитесь, что база данных доступна, а переменная `DATABASE_URL` настроена правильно.

Команды для создания и применения миграций зависят от расположения `alembic.ini` и конфигурации Alembic в проекте. Их следует выполнять из соответствующего рабочего каталога приложения.

## Design Decisions

### 1. Разделение на слои

Проект использует принципы Clean Architecture: доменная логика отделена от инфраструктуры и HTTP-слоя.

Это снижает связанность компонентов, упрощает тестирование и позволяет изменять реализации внешних зависимостей без существенного изменения бизнес-логики.

### 2. Асинхронный клиент Deribit

Для HTTP-запросов используется `aiohttp`. Клиент вынесен в отдельный компонент и работает через асинхронный контекстный менеджер.

Это позволяет управлять временем жизни HTTP-сессии и эффективно выполнять сетевые операции.

### 3. Celery для фоновых задач

Сбор цен вынесен из HTTP-запросов в отдельную фоновую задачу. Celery Beat отвечает за расписание, а Celery Worker выполняет задачу.

Так API не зависит от длительности получения данных с биржи. Redis используется для передачи задач между компонентами Celery.

### 4. Асинхронная работа с PostgreSQL

SQLAlchemy Async и `AsyncSession` используются для взаимодействия с PostgreSQL.

Работа с данными инкапсулирована в репозиториях, а FastAPI получает сессию через механизм dependency injection. Это помогает разделять ответственность и упрощает тестирование.

### 5. Разделение доменной логики и хранения данных

Доменная сущность цены не зависит напрямую от конкретной ORM-модели. Репозиторий отвечает за сохранение и получение данных, а сервис — за бизнес-операции.

Такое разделение упрощает сопровождение и изменение отдельных компонентов.

### 6. Unix timestamp

Время получения цены хранится в формате Unix timestamp. Это позволяет однозначно фиксировать момент получения данных и выполнять выборки по временному диапазону.

### 7. Docker Compose

API, Celery, PostgreSQL и Redis запускаются как отдельные сервисы. API и Celery используют общий Docker-образ, но запускаются с разными командами.

Это упрощает локальное развёртывание и делает окружение воспроизводимым.

### 8. Обработка ошибок

Ошибки получения данных обрабатываются отдельно для каждого тикера. Ошибки сохранения данных приводят к откату транзакции и передаются механизму повторного выполнения Celery.

Такой подход позволяет не прекращать обработку всех тикеров из-за единичной ошибки внешнего API.
